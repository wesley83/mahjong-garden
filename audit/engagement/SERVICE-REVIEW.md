# Challenge service coverage review before setup

The requested shared Daily Garden/friend standings need a separate collection: /mahjong-challenges.html, type MahjongChallengeV1. The existing campaign/history services retain their exact policy and record formats. Client pure tests currently pass, including two alias keys on one exact deal, immutable retry after lost response, strict native trigger validation and historical payload compatibility.

The new policy grants anonymous POST only at #scores, accepts one exact li/meta grammar, binds canonical challenge/level/original pair count/rules, assistance base, stars, bounded active seconds and normalized alias key, and keeps per-alias/challenge uniqueness. Dates/weekly modes/seed bounds are checked; future daily/week submissions are rejected using service UTC time. Public aliases remain unauthenticated and client-reported; no identity/anti-cheat claim. No owner credential enters files or browser code.

Setup first takes a verified full local backup, creates a uniquely named owned fixture and proves native controls before create-only production discovery/setup. Exact existing policy mismatch is retained and refused. Isolated fixture verifies valid two-name POSTs, duplicate/case aliases, bad score/pairs/rules/key/markup/selector refusal and forbidden public PUT/DELETE. Production repeats bounded POST/duplicate/invalid/selector checks with benign owned records. Destructive public method probes are confined to the disposable exact-policy fixture. Conditional cleanup removes only explicitly owned keys and verifies all other service content; fixture deletion is restricted to its generated nonce path. The root game and old score services are never written by setup.

Record actual service policy hash, backup, attempts, cleanup and probe scope in challenge-server.json, then require the new receipt in the application release gate. Client/UI/native/PWA evidence and full release review remain required before root publication.
